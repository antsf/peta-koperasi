# civic-tech-review

Review a feature, decision, or change through the lens of civic technology principles for the Koperasi Desa Merah Putih Map project.

## When to use

Run this skill when reviewing any new feature proposal, architectural decision, dependency addition, or policy change. Also run when someone proposes something that "sounds reasonable technically" but may have civic implications — analytics, gamification, registration requirements, data restrictions, or complexity increases.

## Activation

Trigger: user says "civic tech review", "civic review", "is this civic-appropriate", "does this serve the community", or invokes `/civic-tech-review`.

## Instructions

You are reviewing a feature or decision through the lens of civic technology principles. This is not a regular web application — it is a public-interest tool that serves Indonesian communities mapping their own cooperatives. The standards for what is acceptable are different from commercial software.

Work through each section below. For each test, explain how the feature under review passes or fails, and provide concrete reasoning.

---

### 1. What Makes This a Civic-Tech Project

Before reviewing, internalize these distinctions. This is NOT just a web app:

- **It serves public interest,** not business metrics. Success is measured by whether Indonesian villages can find and verify their cooperatives, not by engagement, retention, or revenue.
- **It handles community-generated data.** The data belongs conceptually to the communities that contributed it, not to the platform operators.
- **Its users include people with limited digital literacy.** A retiree in a rural Javanese village is as much a target user as a tech-savvy university student in Jakarta.
- **Its impact is measured by civic outcomes.** Did a village find a cooperative they did not know about? Did a researcher use the data to study cooperative coverage gaps? Did a local government use the map for planning?

---

### 2. The Four Civic-Tech Tests

Apply ALL four tests to the feature or decision under review. A feature must pass all four to be acceptable.

#### Test 1: Equity

**Question:** Does this work for users on budget phones, slow connections, and limited digital literacy?

Review criteria:
- Does the feature assume a desktop browser or fast connection?
- Does it require downloading additional JavaScript (how much)?
- Does it use language, iconography, or interaction patterns unfamiliar to rural Indonesian users?
- Does it require multiple steps that assume familiarity with web applications?
- Does it degrade gracefully when the connection is slow or intermittent?
- Would a 55-year-old cooperative treasurer in rural Kalimantan be able to use this without help?

**Flag if:**
- Feature requires >50kB additional JS — **WARNING** (justify against equity cost)
- Feature uses English-only UI elements — **CRITICAL**
- Feature requires interaction patterns uncommon on mobile (drag-and-drop, multi-select, right-click) — **WARNING**
- Feature does not work offline or on intermittent connections when it could — **INFO**

#### Test 2: Openness

**Question:** Does this keep data accessible to everyone, including non-users of this platform?

Review criteria:
- Does the feature lock data behind the platform? (requiring an account to see data, requiring the app to access data)
- Does it use proprietary formats or APIs that make data harder to extract?
- Is the data generated by this feature re-usable by researchers, NGOs, and government without signing up for anything?
- Does it create dependencies on specific vendors or services?

The project's data should be, in principle, exportable and usable by anyone. Even without a formal data export API in v1, the architecture should not make future export harder.

**Flag if:**
- Feature locks data behind registration or API keys — **CRITICAL**
- Feature stores data in a format that is hard to export — **WARNING**
- Feature creates vendor lock-in that would be expensive to reverse — **WARNING**

#### Test 3: Accountability

**Question:** Can the community understand how their data is used and governed?

Review criteria:
- Does the feature make data processing transparent or opaque?
- If the feature involves automated decisions (approval, removal, ranking), can a community member understand why a decision was made?
- Does the feature collect data beyond what is needed for its stated purpose?
- Is there a clear explanation of what data is collected and why?

**Flag if:**
- Feature collects data not needed for its stated function — **CRITICAL**
- Automated decisions with no transparency (black-box moderation, hidden ranking) — **WARNING**
- No explanation of data collection purpose — **WARNING**

#### Test 4: Sustainability

**Question:** Can this be maintained by a small volunteer team indefinitely?

Review criteria:
- Does the feature add operational complexity (new services to monitor, new APIs to maintain, new databases to back up)?
- Does it require ongoing costs (paid APIs, SaaS subscriptions)?
- Does it require specialized knowledge to maintain (ML models, complex algorithms)?
- Can a new volunteer contributor understand and modify this feature without extensive onboarding?
- Does it increase the project's bus factor risk?

**Flag if:**
- Feature requires a paid service with no free tier — **CRITICAL**
- Feature requires specialized ML/AI knowledge to maintain — **WARNING**
- Feature adds a new database, queue, or external service — **WARNING**
- Feature significantly increases code complexity with limited civic benefit — **WARNING**

---

### 3. The "Gotong Royong" Governance Review

"Gotong royong" (mutual cooperation) is the Indonesian cultural principle of communal work. This project embodies it: anonymous contributions, community voting, no central authority.

**Review whether the feature reinforces or undermines community self-governance:**

- Does it create a privileged class of users (admins, moderators, "verified" users)?
- Does it centralize decision-making that should be distributed?
- Does it require a central operator to function (manual approval queues, content moderation dashboards)?
- Does it shift power from the community to the platform?

**Flag if:**
- Feature introduces admin roles or privileged access — **CRITICAL** (violates architectural decisions)
- Feature centralizes decisions currently made by community voting — **WARNING**
- Feature creates dependency on a central operator — **WARNING**

---

### 4. When a Technically Correct Feature Is Civically Wrong

Some features are good engineering practice but wrong for this project. Review against these specific examples:

1. **Analytics/tracking:** Understanding user behavior is normal for web development. For this project, it violates user privacy and soul.md's principles. No Google Analytics, no Mixpanel, no Hotjar, no custom event tracking.

2. **User accounts/profiles:** Registration improves data quality in many platforms. For this project, it creates a barrier to contribution and contradicts the anonymous-participation model.

3. **Gamification (badges, points, leaderboards):** Gamification increases engagement. For this project, it incentivizes gaming the system and shifts motivation from civic contribution to personal reward.

4. **Content moderation dashboard:** A moderation tool sounds responsible. For this project, it creates an admin class that contradicts community self-governance.

5. **AI-powered spam detection:** ML spam filters are effective. For this project, they add complexity a volunteer team cannot maintain and make decisions the community cannot understand.

6. **Data monetization or "premium" features:** Sustainability through revenue is normal. For this project, it would betray the public-interest mission.

**Flag if:**
- Any of the above patterns are proposed — **CRITICAL** with explanation of civic harm

---

### 5. The Open Data Question

Review whether the feature affects data openness:

1. **Can the data generated by this feature be accessed without the platform?** The cooperative locations, names, and addresses should be extractable via database export. No feature should make this harder.

2. **Does the feature store data in platform-specific formats?** Geographic data should remain in standard formats (GeoJSON, WKT, lat/lng).

3. **Could a researcher, NGO, or government agency use this data for their own analysis?** If the feature adds metadata, is that metadata useful outside this platform?

4. **Does the feature require the platform to be running for the data to be useful?** Data should have value independent of this specific application.

---

### 6. Civic-Tech Anti-Patterns

Flag if any of these patterns are present:

1. **Surveillance creep:** Collecting more data "just in case" or "for future features." Only collect what is needed now for a specific stated purpose.

2. **Complexity ratchet:** Each feature adds a little complexity. Over time, the project becomes unmaintainable by volunteers. Every feature must justify its maintenance burden.

3. **Tech-literacy bias:** Features that only benefit tech-literate users while making the experience confusing for less digital-literate users.

4. **Platform capture:** Making data or features dependent on this specific platform rather than the open web.

5. **Engagement farming:** Optimizing for time-on-site, return visits, or notification clicks rather than civic utility.

6. **Paternalism:** Making decisions "for" the community rather than providing tools for the community to self-govern.

---

### 7. Review Checklist

- [ ] Equity test: works on budget phones, slow connections, limited digital literacy
- [ ] Openness test: data remains accessible to everyone
- [ ] Accountability test: data collection and decisions are transparent
- [ ] Sustainability test: maintainable by a small volunteer team
- [ ] Gotong royong: reinforces community self-governance
- [ ] Not a disguised anti-pattern (analytics, gamification, admin roles, etc.)
- [ ] No surveillance creep (collects only needed data)
- [ ] No complexity ratchet (maintenance burden justified by civic benefit)
- [ ] No tech-literacy bias (usable by all target users)
- [ ] Open data principles maintained
- [ ] Consistent with soul.md principles
- [ ] Consistent with project architectural decisions

---

### 8. Exit Criteria

The review is complete when:

1. All four civic-tech tests have been applied with clear PASS/FAIL and reasoning
2. The gotong royong governance review has been completed
3. All civic-tech anti-patterns have been checked
4. Any CRITICAL findings include a recommendation to reject or substantially redesign the feature
5. Any WARNING findings include specific modifications that would make the feature civically acceptable
6. A final verdict is provided: APPROVE, APPROVE WITH MODIFICATIONS, or REJECT
7. The verdict includes a one-paragraph civic impact statement explaining how this feature serves or harms the project's public-interest mission
